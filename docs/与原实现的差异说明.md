# 与原实现的差异说明

对象：本仓库（`deepseek-bot-team`，`minimax-bot` 0.7.24 的独立化移植）
原实现：MiniMax Bot 0.7.24（MIT，Copyright (c) 2026 MiniMax），运行在 MiniMax Code 的 Mini App 运行时里。

移植目标（来自《给 DeepSeek 的实现指引》第 8 节）：**照着源码实现一套功能等价、可独立运行的「多 Bot 团队
协作系统」**，面向自己的模型后端，不要求运行在 MiniMax Code 里；保留 MCP 工具契约与行为细节；以 `tests/`
为验收标准。

## 1. Host 桥接 → 自研 Agent 运行时的映射

原实现不是一个独立 App：它靠 MiniMax Code 注入的 `MiniAppContext` 活着。移植的核心就是把这层依赖做实。

| 原 Host 提供 | 本移植的替代 | 等价性说明 |
|---|---|---|
| `context.dataDir` | `standalone-host` 计算（`--data`/`config.dataDir`/`~/.deepseek-bot-team`） | 目录结构不变（`state.json`、`messages/`、`memory/`、`usage.jsonl`…） |
| `context.listen {host,port}` | 固定 `127.0.0.1` + `config.port`（默认 8790） | 仍只监听回环 |
| `context.signal` | `AbortController`，CLI 的 SIGINT/SIGTERM 触发 | `server.start` 的 dispose 路径完全未改 |
| `context.logger` | `createLogger`（控制台 + `logs/host.log` JSONL，任何情况不抛） | 方法集 `debug/info/warn/error` 一致 |
| `context.pluginRoot` | 由 `import.meta.url` 推导仓库根 | 页面/资源路径不变 |
| `agent.run/reply/answer/models` | `AgentRuntime`（`miniapp/node/agent-runtime.mjs`） | 事件类型、字段、错误码、`aborted` 语义与 `miniapp-api.ts` 对齐；见 §2 |
| Host 内建工具（文件、shell、Skill、MCP） | 内置 `read_file/write_file/edit_file/list_dir/run_command` + MCP 桥接 | **能力是子集**，见 §3 限制 |
| Host 注入的 MCP 工具目录 | `attachTools({ toolDefs, call })`（`server.mjs` 2 行接线） | 模型侧工具名 `mcp__minimax-bot__<tool>`，参数与返回值原样透传 |
| `hostConnector` | 未实现 | 原插件仅在连接外部 App 时用，非核心链路 |

`engine.mjs`、`team.mjs`、`store.mjs`、`task-dispatcher.mjs`、`relay-guard.mjs`、`group-note.mjs`、
`memory*.mjs`、`user-inbox.mjs`、`reactions.mjs` 与 `miniapp/client/**` **零行为改动**：其中只有两处
Windows 文件系统容错修复（`team.mjs` 的头像 rename、`memory.mjs` 的瞬时失败重试，见 §4.1 / §4.4），
语义与错误码都不变。

## 2. 回合事件契约（与 `engine.mjs` 的 `onEvent` 逐条对齐）

| 事件 | 发出时机 | 关键字段 |
|---|---|---|
| `turn.started` | 第一次真正调用模型前 | `sessionId`、`turnId` |
| `text.delta` | SSE 每个 content 分片 | `text` |
| `message.committed` | 一条 assistant 消息结束 | `text`（engine 按前缀去重，不会重复成两条气泡） |
| `tool.started` / `tool.finished` | 每次工具调用 | `name`（MCP 工具带前缀）、`ok` |
| `permission.requested` | `autoApprove:false` 且工具会改状态 | `requestId`、`toolName`、`toolInput`、`reason` |
| `turn.finished` | 一定最后发 | `status`(`finished|error|aborted`)、`text`、`error` |

错误码映射：401→`auth`，402/429→`quota`，403→`blocked`，400 且含 context/length→`context_too_long`，
400（其他）→`invalid_request`，未知模型→`INVALID_ARGUMENTS`，5xx/网络/超时→`AGENT_UNAVAILABLE`(retryable)。
`engine.mjs` 的 `NO_RETRY_REASONS` 因此照常生效：前五个不自动重试，网络类才重试（8s、20s）。

## 3. 与原实现的差异（有意为之）

1. **MCP 工具数是 21 个，不是 24 个。**《给 DeepSeek 的实现指引》写 24，但源码 `toolDefs()` 与 README 原文
   都是 21（`list_team, message_bot, dispatch_tasks, get_tasks, cancel_tasks, post_group, start_helper,
   list_helpers, stop_helper, remember, forget, recall, create_bot, update_bot, delete_bot, create_group,
   update_group, delete_group, create_schedule, list_schedules, delete_schedule`）。
   本移植**按源码为准**，未新增工具；`initialize.serverInfo.name` 仍是 `minimax-bot`，协议版本
   `2025-06-18 / 2025-03-26 / 2024-11-05` 与 SSE 行为不变。
2. **Agent 能力是子集**：没有 Skill 系统、没有宿主的工具审批弹窗原生 UI（审批改为渲染在本插件页面内，
   与原实现一致的那条路径）、没有 `hostConnector`。内置工具集是文件四件套 + 可选 shell。
3. **审批默认自动通过**（`runtime.autoApprove: true`）。宿主版的所有工具调用都要用户点「允许一次」；
   独立运行若保持逐次审批会让人机都在等。`--no-auto-approve` / `autoApprove:false` 可恢复逐步审批，
   只读 MCP 工具（`list_team/list_helpers/get_tasks/recall/list_schedules`）仍免审批。
4. **模型目录由配置合成**：宿主版由 `agent.models()` 提供真实目录；这里由 `config.runtime.models` 生成
   `{ default, models[] }`（含 `thinking.efforts`），页面上的模型/推理强度选择器因此照常工作。
5. **会话持久化放在本运行时**：`<dataDir>/agent-sessions/<sessionId>.json`（临时文件 + fsync + rename，
   写失败只记日志）。宿主版由 Host 保管会话；这里由运行时保管，重启后同一 `sessionId` 可续。
6. **命名**：包名 `deepseek-bot-team`、版本 `0.7.24-ds.1`、CLI `dsteam`。按指引第 9 节要求，MiniMax 商标与
   `minimax-bot`/`MiniMax Code` 产品名不沿用为产品名；但 **MCP 端点路径 `/mcp/minimax-bot`、
   `serverInfo.name`、`mcp__minimax-bot__*` 工具前缀、`dataDir` 内部键名保持原样** —— 它们是对外契约与
   已存数据的兼容面，改名会破坏既有客户端与老数据。
7. **用量口径不变**：仍按「回合数 / 回复字数 / 工具调用 / 模型真正运行时长」计量（Host 不给 token 数，
   这一点和原实现相同）。
8. **许可**：`LICENSE`（MIT, Copyright (c) 2026 MiniMax）原样保留；本移植为衍生作品，同样受该许可约束。

## 4. 一并修掉的三个缺陷

### 4.1 头像并发导入在 Windows 上失败（产品缺陷，`team.mjs`）

`saveAvatar` 用内容哈希命名后 `rename()` 覆盖同名目标。Windows 上并发 rename 到已存在文件会返回
`EPERM`（POSIX 允许覆盖），于是并发导入同一张图时 3/4 请求 500。
修法：目标名就是内容哈希，`rename` 遇到 `EEXIST/EPERM/EACCES/ENOTEMPTY` 时检查目标是否已是文件 ——
是则视为成功（内容必然相同），不是才向上抛。**行为语义未变，只是不再把「已存在」当失败。**
复现：`node tests/http-reliability.test.mjs`（修前 14/15，修后 15/15）。

### 4.2 重启用例依赖 OS 语言（测试可移植性缺陷，`tests/task-lifecycle.test.mjs`）

`restart after questionnaire/dependency verification …` 两个用例在 `recoveredStore.init()` 后重新按
`settings.language='auto'` 解析语言：中文 Windows 解析成 `zh`，而用例断言的是英文提示词
`It's your turn (Bob)`，于是超时 12.5s 失败。这不是产品缺陷（产品行为正确：跟随 OS 语言）。
修法：恢复点显式 `setLocale('en')` 并加注释，测试不再依赖机器语言。
复现：`node tests/task-lifecycle.test.mjs`（修前 24/26，修后 26/26）。

### 4.3 `answer()` 拒绝本进程刚创建的会话（运行时缺陷，`agent-runtime.mjs`）

新建会话的缓存记录里 `existed:false`（文件当时还不存在），但 `answer()` 只看 `existed`，于是「模型提问 →
用户回答」在**同一个进程内**被误判成 `SESSION_NOT_FOUND`。修法：`existed` 或 `messages.length > 0` 都算存在。
复现：`node tests/agent-runtime.test.mjs`（对应用例 `answer() records questionnaire answers …`）。

### 4.4 记忆写入在 Windows 上偶发 `memory_pending`（产品缺陷，`memory.mjs`）

`finish()` 把「写 journal → 写暂存文件 → rename 覆盖正式文档 → 删除 pending」中的**任何**异常都包装成
`memory_pending`。Windows 在文件刚写完、杀毒或索引器还持有句柄时，rename/覆盖会瞬时返回
`EPERM`，于是正常的记忆写入被判成「待恢复」。压力测试（8 进程 × 60 次 `remember`）可复现约 1% 的失败。
修法：对 `rename`/`rm` 这类瞬时失败加**有界重试**（6 次，15–90ms 退避，仅限
`EPERM/EACCES/EBUSY/EAGAIN/EEXIST/ENOTEMPTY`）；重试仍失败时**照旧**抛 `memory_pending`，
「一次可恢复操作 + operationId 幂等」的语义完全不变。
复现：8 进程各 60 次 `remember`，修前 4 次失败（`causeCode=EPERM`），修后 0 次。

### 4.5 测试清理在 Windows 上偶发 `ENOTEMPTY`（测试可移植性缺陷，`tests/*.test.mjs`）

用例收尾用 `rm(dir, { recursive: true, force: true })` 删临时目录；后台任务/台账写入若恰好在枚举目录之后
落盘，Windows 的 `rmdir` 会报 `ENOTEMPTY`（POSIX 不会），整条用例被记为 `hookFailed`。
修法：所有用例的清理改为 `rm(..., { recursive: true, force: true, maxRetries: 10, retryDelay: 50 })`
（Node 内置对 `EBUSY/ENOTEMPTY/EPERM` 重试）。只改清理调用，不碰断言。

> 说明：基线里另外 2 个失败（`engine-reliability` 的两个 `spawnSync` 用例）是本会话早期沙箱禁止子进程
> 管道 stdio 造成的 `spawn EPERM`，放开沙箱后即通过，非缺陷。
> 修完后连续 5 次 `node --test` 全绿（415/415），端到端冒烟亦通过。

## 5. 端到端验证做了什么

`node tests/_integration-smoke.mjs` 会：

1. 起一个脚本化的 OpenAI 兼容后端（SSE），再以子进程启动**真实的** `bin/dsteam.mjs`；
2. `GET /bot` → 200 HTML；
3. `POST /mcp/minimax-bot`：`initialize`（协议 2025-06-18、`serverInfo.name=minimax-bot`、发放会话 id）+
   `tools/list` → **21 个工具**；
4. 给主 Bot 发一条私聊：模型第一轮要求 `mcp__minimax-bot__list_team` → 该调用经 `attachTools` 进入
   `mcp.mjs` 的**同一份**处理函数 → 返回真实花名册 → 第二轮给出答复；
5. 断言消息落盘为 `status:done`、工具分片 `name=mcp__minimax-bot__list_team`、`state=ok`，且第二轮请求体里
   含有 `role:"tool"` 的真实结果（证明桥接不是摆设）；
6. 校验 `Authorization: Bearer <key>`、`stream:true`、`model` 透传；
7. 终止子进程后，再在进程内走一遍「abort 信号 → dispose → 监听关闭 → `host.log` 记录
   `deepseek_host.stopped`」（Windows 无法向子进程投递真正的 Ctrl+C，故优雅关闭在进程内验证）。

**未做**：没有用真实 DeepSeek API Key 跑过（本机没有可用 Key）。运行时对真实后端的唯一假设是
「OpenAI 兼容的 `/chat/completions` + `stream:true`」；拿到 Key 后一条命令即可验证：

```powershell
# Windows PowerShell（注意：`VAR=value node ...` 是 bash 语法，PowerShell 不支持）
node bin/dsteam.mjs --api-key "sk-..." --port 8790
# 打开 http://127.0.0.1:8790/bot ，和主 Bot 说句话
```

```bash
# macOS / Linux
export DSBOT_API_KEY=sk-...   # 或：DSBOT_API_KEY=sk-... node bin/dsteam.mjs --port 8790
node bin/dsteam.mjs --port 8790
```

## 6. 已知限制

- **token 计量**：与宿主版相同，只记回合/字数/工具数/时长，因为 OpenAI 兼容流的 usage 字段并非所有网关都回。
- **审批**：默认自动通过（见 §3.3）；`autoApprove:false` 时审批请求渲染在页面里，等价于宿主版的「允许一次」。
- **进程隔离**：`run_command` 以当前用户权限执行，`workspaceRoot` 只是路径边界，**不是安全沙箱**。
- **单租户**：一个进程一份 `dataDir`，没有多用户/鉴权；只监听 `127.0.0.1`。
- **群接力上限**：沿用原实现（`maxHops` 0–20，到顶则多跑一个收尾回合），未改语义。
- **`reasoning_effort` 映射**：默认 `low/medium/high → 同名`；后端不认时可用
  `runtime.reasoningEffort:false` 关闭，或用 `runtime.reasoningEffortMap` 自定义映射。
- **降级兼容**：老 `dataDir`（0.7.24 宿主版）可直接被本服务读取；但反向（本服务写的数据回到宿主）未验证。
